## 4. How to undo the changes outside the repository

All originals are in `/home/chromebox/nvr_settings_backup_2026-11-10/` (95 files).

1. **Camera metadata and NVR triggers (everything in 3.2 and 3.3):**
   `python3 /home/chromebox/nvr_settings_backup_2026-11-10/restore_settings.py`
   It reads `changes.json` and puts back exactly the metadata files and trigger files listed there, one request at a
   time, with a fresh login for each. It changes nothing else. It was fixed on 10 Nov to log in afresh for every
   request, because a shared login gave HTTP 401 from the NVR. It was syntax-checked but **never run**.
2. **Garage3 only (back to "record only"):** the restore script includes channel 17, because its three triggers are in
   `changes.json`. To do only that one, copy `ch17_VMD.xml`, `ch17_linedetection.xml` and `ch17_fielddetection.xml`
   back with `PUT /ISAPI/Event/triggers/<event>-17` on the NVR (`192.0.0.99`).
3. **KVision's configuration:** close KVision first (it rewrites the file when it exits), then copy
   `~/.config/KVision/KVision.conf.before-nvr-list-2026-11-10` over `~/.config/KVision/KVision.conf`.
4. **Firmware:** not reversible with a script here, and downgrading is not advised. The only older firmware on hand is
   `Firmware__V5.7.19_241207_S3000618481.zip` in `/home/chromebox/NFS/HikVision Firmware/DS-2CD2387G2-LSUSL/`, built

## 5. Findings (what was learned, with how sure we are)

**Sure (seen directly):**
- A camera's own event stream (`/ISAPI/Event/notification/alertStream`) carries the target: `targetType` on motion,
  `detectionTarget` on line crossing and intrusion, with a box and the channel. Firmware V5.7.19 sent no labels on the
  2347 cameras; V5.7.23 does.
- The recorder's event stream carries the **same labelled XML for every channel** once three things are on: the
  camera's metadata (Smart Event), the rule enabled on the camera, and the centre action on the recorder's trigger.
  Until Garage3 had all three, the recorder sent nothing for it. We first concluded the recorder could not relay
  labels; that was wrong, and caused by Garage3's settings.
- The recorder's SDK alarm channel (`NET_DVR_SetupAlarmChan`) gives line crossing and intrusion with a box and a
  picture, but **no target word**. Motion arrives as a header only. Smart events from it need the "motion target
  picture" arming bit (`bySubScription` 0x80); with the plain arming only "duration" messages arrived.
- The recorder's recorded event log (the red marks on the playback timeline) holds no target type.
- A motion zone must be drawn on the camera for motion to be reported at all. Garage3 had motion on and no zone.
- Line detection, intrusion and metadata on Garage3 were found switched off at one point without the owner knowing
  why; fixed by hand.

**Likely, not proven:**
- The recorder route shows no pause between reports. In one run Garage3 gave line crossings 5 s and 11 s apart, and
  a line crossing and an intrusion in the same second. The earlier misses may have come from settings, not from a
  pause. See 7.
- `targetNvrOnCameras` emptied itself because an offscreen test run of the application saved an empty list.

**Method notes:** the NVR answered some read requests with HTTP 401 in the middle of a long run of requests when one
login session was reused across the cameras and the NVR. Using a fresh digest login per request, with about 1.5 s
between requests, fixed it. Nothing was locked out at any point.

## 6. Reads that answer "why no events" (all read-only, over HTTP with the recorder's login)

For a camera behind the NVR (`NVR` = the recorder address, `CAM` = the camera's own address, `N` = its NVR channel):

| Question | Request | Healthy answer |
|---|---|---|
| Is the camera online in the NVR? | `GET NVR/ISAPI/ContentMgmt/InputProxy/channels/N/status` | `<online>true</online>` |
| Firmware new enough to label targets? | `GET NVR/ISAPI/ContentMgmt/InputProxy/channels/N` | `firmwareVersion` V5.7.23 or later (2347 family) |
| Is the smart-event metadata on? | `GET CAM/ISAPI/Streaming/channels/101/metadata` | `behaviorAnalysis` with `<enable>true</enable>` |
| Is motion detection on, with a zone? | `GET CAM/ISAPI/System/Video/inputs/channels/1/motionDetectionExt` | `<enabled>true</enabled>` and a region |
| Are the smart rules switched on? | `GET CAM/ISAPI/Smart/LineDetection/1` and `.../FieldDetection/1` | overall `<enabled>true</enabled>`; a rule's own flag can read false while it still fires |
| What targets does a rule look for? | same two requests | `<detectionTarget>` lists human, vehicle, others |
| Does the NVR relay events to us? | `GET NVR/ISAPI/Event/triggers/<event>-N` for `VMD`, `linedetection`, `fielddetection`, `regionEntrance` | `<notificationMethod>center</notificationMethod>` present |

A wrong login counts toward a camera lock-out, so these must only be sent with a login known to be right.

## 9. Added on 11 Nov 2026 (not committed when written)

- **Event-picture check.** With the overlay switch ON, Garage3's event pictures carry a red outline on the reported
  target rectangle (and the rule line; sometimes a red border round the whole picture). With it OFF they are clean
  photos. The switch is not in any ISAPI path tried (about 70, snapshots before and after differed in none).
  KVision judges each picture by testing whether the four edges of the reported `TargetRect` are red. On 6 real
  pictures the rectangle gave 0.95-1.00 on three or more sides; the same box moved elsewhere gave 0.00-0.05, and
  the clean picture gave 0.00-0.01. Replayed through the new code: frame-on camera reads `on`, clean camera `off`.
- **Unexplained camera change.** Garage3's video bitrate (`constantBitRate`, `vbrUpperCap`) went from 4096 to 3072
  between two snapshots taken while the overlay switch was saved twice in the web page. KVision wrote nothing. Left
  as the camera has it.
- Garage3 triggers (channel 17 VMD, line, intrusion) still carry a temporary centre action; originals and
  `restore_settings.py` are in `/home/chromebox/nvr_settings_backup_2026-11-10/`.
- Credit: Supergiovane/node-red-contrib-hikvision-ultimate was read for how events and pictures are handled; it has
  nothing on this switch.
- **Pictures through the recorder.** The recorder's event stream carries no picture: each event says
  `detectionPictureTransType url` and gives a `bkgUrl` (`/picture/Streaming/tracks/<n>/?name=...`). A GET on it with
  the recorder's digest login returns the JPEG (800x480 on channel 16, with the blue rule outline and a red target
  box). A camera's own stream attaches the picture instead (`binary`). KVision handles both, keeps the newest 100 in
  `logs/pictures`, and sends the login only to the recorder that sent the link. node-red-contrib-hikvision-ultimate
  only passes on pictures that arrive on the stream (`onImage`) and the `picUrl`/`picName` text; it never downloads
  the link. Its README says its image pin works "only if the camera/NVR actually sends a picture on the alert stream".
- **Missed line and intrusion events on a camera's own stream (11 Nov, found on Livingroom-New).** The camera sends
  the event's picture first and then the XML. `onReadyRead` turned the buffer into text with
  `QString::fromLatin1(QByteArray)`, which stops at the first zero byte, so everything after the picture was hidden and
  the events were never seen. A raw listener saw dozens of `linedetection` and `fielddetection` events in a minute
  while KVision's code saw one motion event. With the length given explicitly the same camera produced 2 line, 3
  intrusion and 5 motion reports in 20 seconds. The recorder connection was unaffected (it sends links). Also
  added: a 40 second stall timer, reconnect with growing waits, and no repeat asking after HTTP 404/405/501.
- **Rules that live in the recorder (11 Nov).** Driveway (ch 16, 192.0.0.40): the camera's own intrusion rule 1 is the
  red zone near the steps (matches the user's screenshot of the camera page), but the saved 06:12:39 picture showed a
  blue zone the camera does not have. The recorder has its own `/ISAPI/Smart/FieldDetection/16` with zones 1 and 3,
  and zone 1's corners match the blue shape (after the 1000 scale and the vertical flip). Earlier I wrongly read the
  camera's per-zone `<enabled>` flag as "rule off"; the camera page shows Rule 1 on while the flag reads false, so the
  flag is not used. The setup check now reads the recorder's four rule kinds and notes where a rule lives. Not proven:
  that the 06:12:40 event itself came from the recorder's rule (its XML was not captured).

### 10.3 Findings (with how sure we are)

- **The camera's own hours gate the NVR's audio and light actions.** The Front Door's audible alarm is armed only
  00:00-05:45 and 21:00-24:00, every day (read from `/ISAPI/Event/triggers/notifications/AudioAlarm?format=json`, and it
  matched the camera's page). The NVR's rule for intrusion on that channel lists the audio and is armed all day, yet the
  audio does not sound by day. This is the likely cause; it was not tested by triggering the event by day and by night.
- **The NVR links cameras to each other's white lights** with `whiteLightOut` actions in its event rules (46 of them);
  only 3 `audioOut` actions exist (SideYard intrusion and line crossing, FrontDoor intrusion). Four of the source events
  are switched off at the NVR: Pano region entrance, FrontDoor line crossing, PTZ intrusion, Driveway line crossing.
- **Face detection** on Livingroom2 / Garage2 (192.0.0.108) is enabled and the camera lists a `facedetection-1` trigger,
  but two live tests (walking in front of it) produced no face event on the camera's or the NVR's stream. It is not known
  whether this model ever sends one. The other cameras checked do not support face detection.
- **Unrecognised event types seen in about 2 minutes on 22 cameras:** `IO` and `duration` only; both are left out of the
  log as noise. A longer run would show rarer types.
- **The Doorbell (192.168.20.185)** answers 404 to the event stream and to the configuration export. It cannot be logged
  or backed up.
- **Image Parameters Switch** is at `/ISAPI/Image/channels/1/displayParamSwitch` (found with the browser's Network tab).
  Modes seen: `disable` (Not Switch), `month` (Scheduled-Switch, a scene per time range per month) and `timingSwitch`
  (PTZ, one schedule per preset). The currently selected scene of a Not Switch camera is not in that request.
- **A camera answers a request for a stream it does not have** (103) with a copy of the main stream, and the whole image
  document has two `brightnessLevel` tags (picture and supplement light). Both caused wrong values in the first version
  of the settings window and were fixed.
