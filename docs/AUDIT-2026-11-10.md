## 4. How to undo the changes outside the repository

All originals are in `/home/chromebox/nvr_settings_backup_2026-11-10/` (95 files).

1. **Camera metadata and NVR triggers (everything in 3.2 and 3.3):**
   `python3 /home/chromebox/nvr_settings_backup_2026-11-10/restore_settings.py`
   It reads `changes.json` and puts back exactly the metadata files and trigger files listed there, one request at a
   time, with a fresh login for each. It changes nothing else. It was fixed on 10 Nov to log in afresh for every
   request, because a shared login gave HTTP 401 from the NVR. It was syntax-checked but **never run**.
2. **Garage3 only (back to "record only"):** the restore script includes channel 17, because its three triggers are in
   `changes.json`. To do only that one, copy `ch17_VMD.xml`, `ch17_linedetection.xml` and `ch17_fielddetection.xml`
   back with `PUT /ISAPI/Event/triggers/<event>-17` on the NVR (`192.0.0.99`).
3. **KVision's configuration:** close KVision first (it rewrites the file when it exits), then copy
   `~/.config/KVision/KVision.conf.before-nvr-list-2026-11-10` over `~/.config/KVision/KVision.conf`.
4. **Firmware:** not reversible with a script here, and downgrading is not advised. The only older firmware on hand is
   `Firmware__V5.7.19_241207_S3000618481.zip` in `/home/chromebox/NFS/HikVision Firmware/DS-2CD2387G2-LSUSL/`, built
   for the **2387** model. There is no V5.7.19 file for the 2347 model in the folders, so the nine 2347 cameras cannot
   be put back to V5.7.19 from what is here. (Note: both folders also hold the same V5.7.23 `digicap.dav`, byte for
   byte; the file in the 2387 folder is the one used on BackYard Full, so check the camera's model before using it.)
5. **Repository:** every commit above can be reverted with `git revert <hash>`. The release can be removed with
   `gh release delete v3.2.0` and `git push --delete origin v3.2.0`.

## 5. Findings (what was learned, with how sure we are)

**Sure (seen directly):**
- A camera's own event stream (`/ISAPI/Event/notification/alertStream`) carries the target: `targetType` on motion,
  `detectionTarget` on line crossing and intrusion, with a box and the channel. Firmware V5.7.19 sent no labels on the
  2347 cameras; V5.7.23 does.
- The recorder's event stream carries the **same labelled XML for every channel** once three things are on: the
  camera's metadata (Smart Event), the rule enabled on the camera, and the centre action on the recorder's trigger.
  Until Garage3 had all three, the recorder sent nothing for it. We first concluded the recorder could not relay
  labels; that was wrong, and caused by Garage3's settings.
- The recorder's SDK alarm channel (`NET_DVR_SetupAlarmChan`) gives line crossing and intrusion with a box and a
  picture, but **no target word**. Motion arrives as a header only. Smart events from it need the "motion target
  picture" arming bit (`bySubScription` 0x80); with the plain arming only "duration" messages arrived.
- The recorder's recorded event log (the red marks on the playback timeline) holds no target type.
- A motion zone must be drawn on the camera for motion to be reported at all. Garage3 had motion on and no zone.
- Line detection, intrusion and metadata on Garage3 were found switched off at one point without the owner knowing
  why; fixed by hand.

**Likely, not proven:**
- The recorder route shows no pause between reports. In one run Garage3 gave line crossings 5 s and 11 s apart, and
  a line crossing and an intrusion in the same second. The earlier misses may have come from settings, not from a
  pause. See 7.
- `targetNvrOnCameras` emptied itself because an offscreen test run of the application saved an empty list.

**Method notes:** the NVR answered some read requests with HTTP 401 in the middle of a long run of requests when one
login session was reused across the cameras and the NVR. Using a fresh digest login per request, with about 1.5 s
between requests, fixed it. Nothing was locked out at any point.

## 6. Reads that answer "why no events" (all read-only, over HTTP with the recorder's login)

For a camera behind the NVR (`NVR` = the recorder address, `CAM` = the camera's own address, `N` = its NVR channel):

| Question | Request | Healthy answer |
|---|---|---|
| Is the camera online in the NVR? | `GET NVR/ISAPI/ContentMgmt/InputProxy/channels/N/status` | `<online>true</online>` |
| Firmware new enough to label targets? | `GET NVR/ISAPI/ContentMgmt/InputProxy/channels/N` | `firmwareVersion` V5.7.23 or later (2347 family) |
| Is the smart-event metadata on? | `GET CAM/ISAPI/Streaming/channels/101/metadata` | `behaviorAnalysis` with `<enable>true</enable>` |
| Is motion detection on, with a zone? | `GET CAM/ISAPI/System/Video/inputs/channels/1/motionDetectionExt` | `<enabled>true</enabled>` and a region |
| Are the smart rules switched on? | `GET CAM/ISAPI/Smart/LineDetection/1` and `.../FieldDetection/1` | overall `<enabled>true</enabled>`; a rule's own flag can read false while it still fires |
| What targets does a rule look for? | same two requests | `<detectionTarget>` lists human, vehicle, others |
| Does the NVR relay events to us? | `GET NVR/ISAPI/Event/triggers/<event>-N` for `VMD`, `linedetection`, `fielddetection`, `regionEntrance` | `<notificationMethod>center</notificationMethod>` present |

A wrong login counts toward a camera lock-out, so these must only be sent with a login known to be right.

## 7. Open questions (not settled today)

1. **Is there a pause between reports from a camera?** Seen: Livingroom-New gave one line-crossing report for two
   crossings 12 s apart, and later none for a crossing 4 minutes after the previous. Garage3, through the recorder,
   gave line crossings 5 s and 11 s apart and two events in the same second. Settings differed between those runs
   (metadata, Target Validity, centre action), so the cause is unproven. The test that would settle it: a counted
   series of crossings, watched on the camera and through the recorder at the same time.
2. **Target Validity** on Garage3 was changed from Basic to High in the web page, but a read-back of the line rule
   showed `alarmConfidence = mediumLow`. Either it had not saved, it is a different rule, or the names do not map
   as assumed.
3. **Why `targetNvrOnCameras` emptied.** Unproven; see 5.
4. **Whether the recorder route labels every camera.** Only Garage3 was watched in detail. Others were set up the same
   way but not watched sending a labelled report.
5. **Whether a dual-lens camera reports each lens with its own channel number** on its one connection.
6. **The Doorbell** did not answer the device-type requests, so it is treated as a camera by default.
